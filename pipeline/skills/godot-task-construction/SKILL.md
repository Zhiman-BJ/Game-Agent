# Godot 短程任务构造

从真实工程中选择一个玩家可完成的功能，保留其工程背景，把核心实现和必要接入留给求解者。产物包含公开需求、基础正常但目标缺失的 start、可行 reference、公平 validator 和可复核证据。按质量合格任务计数；目录数、修改文件数和题面长度都不是质量或难度结论。

先读宿主的当前状态、固定源码与 Godot 版本、已有规格/产物、可用运行命令和预算。从最后一个证据仍有效的阶段继续，不因恢复会话重建整题。批量工作还读候选/合格清单与来源关系。使用用户已选的仓库、范围、工具和预算；只要求沉淀技能时不启动构题、求解或训练。

## 构题与修订主线

1. **运行并选题。** 先走一条真实玩家路径，再追踪输入、状态拥有者、场景/资源/事件和效果消费者。选择能独立验收的功能闭环；记录已有、缺失、待接入关系及最相近候选。范围薄就换边界，目标互不依赖就拆分；不要靠额外命名限制或无关模块增加难度。
2. **证明可行并制造缺口。** 按公开行为做出可运行 reference。区分来源兼容准备、目标补全和目标消融；准备步骤不能预先解决核心难点。保留原入口和非目标系统，一并移除功能机制与必要连接。实际确认 start 的保留行为正常、完整目标缺失。
3. **写需求并校准验收。** 公开操作、结果和必要边界；实现计划、私有测试配方留在构题材料。每条强制判定有公开依据，每项要求有验收出口。先用真实操作和高风险合法/错误变体校准观察，再扩展完整矩阵；默认值、夹具写入、对象发现和等待方式都在审查范围内。
4. **独立挑战并封存。** 审查先只读公开包，再检查参考解、整个测试驱动程序和证据。任务、合法变体、错误变体都须符合各自预期；目标和公开保留行为均有可归因覆盖，必要视觉实际复核。保留原反例，修复受影响部分再验收；公开规格改变则返回设计。所有必要检查完成后固定版本、公开清单和证据。

每次修订写清“问题依据 → 疑似原因 → 有限改动 → 受影响检查 → 观察结果”。start 不能运行先查起点/环境；reference 不通过先区分实现缺陷与误拒；正确变体失败先查隐藏结构假设；错误变体通过先查夹具和观察。不能通过缩窄合理解法、删除反例或把未执行检查填成 PASS 来入集。详细路由见构造与验收参考。

## 机械辅助与结论边界

需要检查来源、reference、start 的字节差异时，可用技能目录下的 `scripts/project_delta.py BEFORE AFTER --output REPORT.json`，或宿主已有的等价工具。它只读两个工程，按脚本/场景/资源等归类增删改并记录哈希；不运行 Godot、不判语义、不生成资格。将差异与功能关系表核对，而非拿文件数作难度评分。宿主负责真实运行、结果聚合、状态与版本校验；没有实现的门槛应报告为接入缺口。

规模、每仓库数量与并发由本批工作单给出，不继承历史批次的配额。分别报告首轮审查与返修后合格数、失败类别、成本和未解决项。33 题经验来自修订后的合格集合，不证明一次构造成功率，也不证明 K3 可解而 Qwen 难解。难度差距只在另行授权、隔离构题上下文的冻结任务求解实验后报告。
