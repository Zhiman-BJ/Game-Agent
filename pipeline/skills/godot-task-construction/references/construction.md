# 制作 reference、start 和公开需求

用于 Construction 及修订。沿用宿主的路径、schema 和命令；此处沉淀构造决策，不另建运行器。进入前读取已通过设计审查的功能边界与关系表；不凭上游 TODO 推断参考解已经存在。

## 先分清三类改动

固定上游后，在隔离副本中建立准备基线与 reference，记录来源关系：

`source → prepared baseline → reference → start`

已有功能消融时 baseline 可能已满足大部分目标；扩展时从 baseline 实现新功能。上图表示可追溯的改动关系，不要求强制建立四份完整目录或固定构造顺序。

| 改动 | 放在哪里 | 判定依据 |
|---|---|---|
| 引擎/资源兼容、非目标依赖修复 | 共同准备，按需要一致用于 start/reference | 缺少它会阻碍声明保留的能力，而它不完成本题核心机制或接入 |
| 目标新功能或目标规则修复 | reference；其缺失对应 start 的工作 | 它直接实现公开目标，即使只有一行，也不能称作准备后送给求解者 |
| 目标消融与必要启动修补 | start | 移除目标机制及连接，同时保留基础运行；启动修补不能恢复目标事务 |

归类以本题边界为准，不以“是不是原仓库 bug”或改动大小为准。同一修复在另一题可能是保留依赖：移动题可以保留正常攻击，攻击题可以保留正常移动；不能用同一预修复副本把两题各自目标都提前完成。记录实际补丁和受影响能力，不只写“兼容修复”。

可用技能的 `scripts/project_delta.py` 或宿主等价工具比较 source/prepared、prepared/reference、reference/start；它提供字节差异和文件类型，语义归类仍由作者完成。工具输出路径放在私有证据区且位于两个输入工程之外。该脚本排除 Git、Godot 缓存等生成内容，拒绝符号链接和特殊文件；运行时保持输入工程不变。未改动但实际参与功能的资源也在关系表中保留。

## 先做出可行的参考闭环

从原入口运行一遍“触发 → 规则与状态变化 → 真实效果 → 必要后续操作”。检查目标和相邻保留能力一起成立，避免只在测试专用场景中证明算法可行。原生基线有目标缺陷时先在 reference 修正，并在来源中明确它不是未经修改的上游答案。

新扩展先确认自然依附的入口、状态拥有者与结果消费者。例如给现有拼图增加保存/继续，应复用原菜单和棋盘重建流程；不能先新做一个独立存档演示，再宣称接入已有游戏。

参考组织方式只是一个可行方案。条件句和时序范围在公开规格中确认；不把 reference 的节点层级、私有信号、纹理 identity 或调度方式悄悄转成要求。若必须新增公共观察接口，先明确其必要性、只读语义和实现自由，再交回设计确认语义变化。

## 沿关系制作完整缺口

从设计的关系表逐条执行消融，关注连接两端：

- 移除目标输入分发或目标监听时，保留公共输入体系与其它功能的分发。
- 移除目标状态/规则时，检查是否有备用脚本或资源已提供同一完整结果。
- 移除目标场景/信号接入时，同时检查序列化引用与动态连接，修复无关悬空引用。
- 保留可复用素材、角色/物品定义、底图和通用能力；只有任务明确要求制作的资源才留作缺失。
- 共享组件只移除目标职责；必要的 no-op 或跳过交接可以保持基础可玩，但不能完成目标状态变化、事务锁或结果提交。

完成后核对实际差异与计划，分别回答：求解者需要实现什么机制、重新建立什么关系、直接复用什么能力。若只差一个预接好的局部空槽，回到设计调整；若基础无法启动或需重建无关系统，收窄删除范围。不要强制所有脚本/场景/资源都产生 diff。

用实际原入口验证 start：导入/启动和声明保留的操作通过，目标不能完整完成。start 可以满足部分子要求；总分 FAIL 本身不能证明消融合理。保留前后证据，明确失败属于缺目标还是工程损坏。

## 从行为契约提炼 instruction

公开材料应让未见参考解的人理解目标与允许的实现。用短目标段说明要实现的功能，随后只保留判定正确性所需的操作、结果、边界和兼容要求；不设置通用词数下限。

将设计信息分流：

| 信息 | 去处 |
|---|---|
| 玩家目标、必要行为、有限保留范围、必需接口及数值 | instruction 或明确引用的公开契约 |
| 给定素材、入口、可运行方式 | 公开工程与必要说明 |
| 为什么选题、依赖探索、参考算法、消融清单、私有 R 编号、测试配方 | 私有设计/构造/覆盖材料 |
| 只为观察方便而要求的节点名、内部存储格式、容器/数组顺序 | 优先改观察器，不新增求解限制 |

每个精确路径、类型、名称、数值或容差说明其产品/兼容理由。已存在的必需接口也要让求解者能从公开材料识别；没有这样的理由就不把 reference 习惯写进题面。“保留原游戏”需落实到相关能力，不能变成隐藏的全游戏测试。

把每个强制条款映射到刺激、观察、合法结果集合和验收出口，并反查每个判分断言的公开依据。目标与公开保留行为同样处理。必要接口文档计入总阅读负担；删重复、实现提示和无关背景，不通过删必要边界或拆文件伪造简洁。

## 校准、交接与局部修订

按 [validation.md](validation.md) 先校准真实操作和高风险观察，再展开完整矩阵。reference 通过证明可行，start 缺失证明任务存在，错误对照检查漏判，实质合法对照检查误拒；它们不能互相替代。

| 发现 | 定位与下一步 |
|---|---|
| start 不可运行或保留行为坏了 | 查依赖/引用/准备与消融交界；修起点，不能把崩溃算目标缺失 |
| reference 不满足公开需求 | 区分实现缺陷与观察误拒；先核实实际行为，不改需求迁就它 |
| 合法变体被拒 | 检查定位、夹具写入、输入、等待、清理与断言的私有假设；验证变体确实合法 |
| 错误变体通过 | 确认缺陷实际触发，再修夹具/观察；保留原反例，不能只换更明显的错误 |
| 实际剩余工作过薄或任务实质重复 | 返回 Design 重设边界或淘汰，不在 Construction 添无关规则 |
| 导入/显示/传输问题 | 保留原执行错误，修运行条件并核对证据失效范围，不作功能结论 |

修复应有具体假设和受影响范围。公共观察函数改动需检查所有调用点；环境或公共准备改变不能只挑旧绿色记录冻结。公开语义改变返回 Design，新 grader 与原判定分别保留。完成状态依据实际检查，不因文件存在而跳过。

## 打包与冻结

公开包只含 instruction、必要公开契约与 start，按显式清单导出。检查答案性注释、完整备份、参考补丁、测试、作者笔记和 Git 历史泄漏；保留来源和许可证。仅扫描文件名不足以证明没有答案。

在不依赖原作者目录、外部绝对路径或旧缓存的副本中运行实际导出包。私有保存 reference、validator、覆盖/对照、修订与原始证据。固定源码/准备、公开规格、两份工程、grader、runner、聚合器及环境版本；缓存排除规则明确一致。后续提交重评保留原判定，用同版 grader 对可比提交重跑，不在看到模型答案后补隐藏需求。
