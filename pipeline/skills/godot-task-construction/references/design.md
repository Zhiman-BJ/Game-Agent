# 从真实工程选择完整功能

用于 Design、范围修订与功能完整性审查。目标是回答“为什么选这一题、留下什么工作、如何判断完成”，不预设固定题型或文件数量。

## 先形成可验证的工程认识

固定源码、资源、引擎和原入口，实际导入、启动并做代表性操作。先读 `project.godot` 的入口/Autoload/输入，再沿相关场景实例、脚本、资源与信号追踪；不要只搜索功能名或 TODO，也不必穷读整个仓库。

沿一条真实操作记录：`玩家入口 → 触发条件 → 状态拥有者 → 场景/资源/事件 → 效果消费者 → 下一次操作`。每条关键关系给真实路径或符号和行为证据。场景序列化的信号、脚本动态连接、资源配置和共享状态都可能参与；静态引用只能提供线索，实际操作才能证明关系有效。未运行时标为待验证，不虚构教程或原作者意图。

已有目标不能正常运行时先分类：导入/依赖问题属于环境或共同准备；目标自身逻辑有缺陷可构成有明确规格的修复；缺少独立玩家目标则不宜构题。不要把未定位的上游故障和目标消融混在一起。

## 选择一个有交付边界的功能

先用一句玩家目标描述结果，再判断：

| 工程证据 | 决策与下一步 |
|---|---|
| 已有功能能跑通，且有真实跨组件协作 | 优先考虑消融；核实删除范围后仍留下核心实现和接入工作 |
| 上游只提供基础，但存在自然扩展方向 | 明确标为扩展；先在原入口证明最小完整参考行为可行，再投入批量构造 |
| 只剩常量、单一判断或现成回调绑定 | 查看核心机制是否已被供应；若几乎全有，换消融边界或淘汰，不靠多删无关文件补难度 |
| 两个目标分别能独立交付 | 考虑拆题；每题保留另一能力作为背景，并分别验证其仍工作 |
| 多个步骤共同实现同一次玩家操作 | 保持为一题，例如两对象协同移动和单次回合结算，不按脚本数拆分 |
| 关键要求无法可靠观察或规格互相冲突 | 先改设计/验收方案；不能到最后用私有阈值迁就 reference |

判断拆分看“不同的完成条件和待补状态变化”，不看菜单项、文件或类的数量。同仓库可以出多题，但每题都要有自己的核心缺口。按本批上限采样，允许一个仓库最终零题。

扩展题在 Design 的探索只需消除主要可行性风险，证明关键行为能接入原入口，并交接探索补丁与未验证项；完整 reference、start 和验收证据由 Construction 完成。不要求 Design 提前生产整套任务，探索成功也不等于任务已合格。

## 用工程关系划定消融边界

在私有设计记录中为关键关系分配下列角色。表用于作者决策，不把路径与实现计划整体复制给求解者。

| 角色 | 如何判断 | 处理 |
|---|---|---|
| 可复用输入与基础 | 美术、地图、角色定义、通用移动等；它们本身不完成目标 | 默认保留及来源归属，减少无关重建 |
| 核心机制 | 决定目标规则、状态更新或关键算法 | 留作求解工作；不能只在完成机制外包一层空函数 |
| 必要接入 | 输入分发、场景挂接、目标信号、资源消费者、结果提交 | 与机制一起选择性移除，让模型负责真实接入 |
| 邻接保留能力 | 目标依赖或可能破坏的已有功能 | 明确有限的公开保留范围，并留下真实操作验收 |
| 可选实现细节 | 参考解内部容器、对象池、私有字段、调度方式 | 不把它们固化为题面或验收接口 |

切断完整功能路径，不等于删除所有相关组件。角色资源和动画素材可保留，触发/应用/提交链仍由模型完成。共享脚本同时承担目标与保留职责时，只移除目标分支；删除整个脚本会破坏基础则改消融位置。为启动保留的最小空实现不得计算目标答案或预建完整事务。

做两个反向检查：

- **缺口不足：**只重新接一根线或返回已有计算结果，能否完成全部目标？若能且核心开发已被代做，重新选边界。代码短不自动意味着薄题，需看真实求解工作。
- **缺口过大：**模型是否必须重造原本应保留的菜单、移动或资产管线才能开始目标？若是，恢复无关依赖，或明确该范围已超出短程题。

只有公开需求确实要求原工程接入时，才据此拒绝独立演示或绕过行为；不因候选选择更简洁的合法实现而判错。

## 识别实际协作难点

下列是读取工程的视角，不是新题配额。按实际存在的关系选择，不要求每题包含全部：

| 关系 | 作者应追问 | 验收方向 |
|---|---|---|
| 一次操作贯穿组件 | 谁触发、谁执行、谁提交？完成信号是否可能重复或提前？ | 真实操作到真实结果，必要的恰好一次与后续可操作性 |
| 多份状态一致 | 棋盘/库存/位置/HUD 哪些表示必须共同变化？谁是事实来源？ | 同时观察实际状态和玩家反馈，不能只看镜像变量 |
| 资源驱动行为 | 配置如何到达每个消费端？保留数据会不会直接供应完整实现？ | 原默认路径及有依据的配置变化，避免夹具覆盖默认值 |
| 生命周期与重入 | 取消、重启、对象增删后旧工作会影响谁？ | 必要的事件边界和新操作，接受合法同步或异步方案 |
| 物理与场景接入 | 碰撞、坐标、实例归属与视觉效果如何共同成立？ | 原生输入/物理/渲染，不能只检查节点存在 |

难点来自真实协作、规则与必要边界，不来自任意命名、文件数或故意缺文档。结构画像只是难度假设；教师/学生差距需要后续独立实测。

## 将决策压缩成可交接记录

复用宿主 proposal/spec/design_report，至少表达以下内容，不增加重复强制 schema：

1. 原工程已观察到的行为、证据、固定版本与准备改动。
2. 一句话玩家目标、完成条件、相邻但不包含的工作。
3. 关键关系的真实位置与“保留/机制缺失/待接入”分配。
4. reference 来源与可行性、start 可运行办法、两种反向检查结论。
5. 公开行为条款、有限保留范围、允许实现变化与观察出口。
6. 最相近候选及实质区别、未解决风险、下一步与阶段资格。

对阶段条件单独核对，例如“进行中保旗”与“终局揭雷”是不同阶段，不能写成冲突的全局规则。新增必要规则必须有来源或明确设计理由；不能把 benchmark 之外的要求冒称其统一规范。

通过设计后仍要根据实际构造验证上述假设。发现消融不足回到范围设计；发现可修的打包或观察问题留在 Construction；薄题或实质重复可直接淘汰。代表决策见 [质量基线与实例](quality-baseline.md)。
