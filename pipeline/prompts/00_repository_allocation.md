# 0. Repository allocation and reusable source brief

Run this stage once per pinned upstream repository before admitting task authors. It allocates distinct task slots and records a navigation brief that all tasks from the same repository can reuse. It is a host/scout stage, not 1–3 independent full-repository explorations.

Inputs: screened repository list, fixed source commit, Godot project path and engine, import/main smoke evidence, historical and benchmark goal registry, and the intended number of candidate slots. Reject a source whose pin or runnable entry cannot be established. The allocation is a candidate plan, not a promise that every slot will become a qualified task.

For each repository, one scout follows the real game entry once and records the main scenes, script/scene/signal relationships, visible gameplay loops and 2–3 plausible complete feature boundaries. The scout should inspect only enough code to establish those relationships. It records observed behavior and uncertainty separately. Share this source-level evidence across sibling slots; assign each slot a different input → state → dependency → visible result → lifecycle boundary. Record closest existing and benchmark goals before assignment. Do not treat different file names or prompts as distinct goals.

Write `planning/allocation.json`, one `planning/source_summaries/<repo>.json`, and one `planning/repository_briefs/<repo>.json` with source revision, selected Godot project and entry, smoke evidence, candidate boundaries, source evidence links and assigned task IDs. A brief may point to a prior first-slot `repo_analysis.md`/`candidate_registry.json` for an already-running batch. `tools/prepare_repository_briefs.py` compiles these existing materials without walking source trees. Preserve the original evidence and fingerprints; rebuild a brief if the source pin or its source documents change.

Each task author first reads its assigned brief and current sibling claims, then verifies only the chosen gameplay path in the pinned project. The author still proves its own reference, start and validator against actual execution. A shared brief does not certify feature feasibility, task qualification, fairness or model difficulty. If a candidate boundary is infeasible or duplicates a sibling, return that slot for reassignment; do not pad the task or broaden a validator to force acceptance.
